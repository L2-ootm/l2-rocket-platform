# Architectural Plan: Closed-Loop CKG Calibration & OpenRocket Mirroring

The recent precision tests revealed a ~20% discrepancy between the Rust AST proxy simulation and the official OpenRocket (OR) Java physics engine. To resolve this and create a perfect evaluation loop for OSIFOG, we will implement a two-pronged strategy: (1) Machine-learned calibration via the CKG (Continuous Knowledge Graph), and (2) Direct algorithmic mirroring of OR's drag equations in Rust.

---

## 1. Option 2: Closed-Loop CKG Delta Feedback (The Machine Learning Approach)

Instead of relying solely on hardcoded physics, we will allow the AST engine to "learn" its own inaccuracies over time and adjust its predictions. We will use the existing `.planning/organic_ckg.json` to store these learned calibration factors.

### Implementation Steps:
1. **The Feedback Loop in `organic_loop.py`**:
   - Currently, `organic_loop.py` only uses OpenRocket validation on the final elite of the last generation. We will add a flag `--calibrate-every N` to run OR validation on the top candidate of *every Nth* generation.
   - When OR validates a rocket, we compare the results: `delta_apogee = or_metrics.apogee_m / rust_apogee_m`.
   - We extract a "Topological Signature" for the rocket (e.g., `Ogive_Nose + 3_Fins_Swept + Cesaroni_Motor`).
   - `organic_loop.py` writes a `calibration_factor` for this signature into the CKG.

2. **The Calibration Proxy in Rust (`l2_engine`)**:
   - `AstEvalBatch` will be updated to accept a `ckg_calibrations: HashMap<String, f64>` payload.
   - Inside `evaluate_ast_inner` (`ast.rs`), the Rust engine will calculate the topological signature of the current candidate.
   - If a matching signature exists in the CKG, it will apply the calibration factor directly to the overall Drag Coefficient ($C_d$) or thrust-to-weight ratio during the `run_trajectory` step.
   - Over successive runs, as the CKG accumulates data, the Rust engine's apogee and mach predictions will mathematically converge to match OpenRocket's output, allowing 100% accurate proxy evaluations at Rust speeds (1000x faster than Java JVM).

## 2. Mirroring Metrics: Aligning the Rust `openrocket` Physics Mode

While the CKG handles dynamic topology calibration, the baseline physics in `l2_engine/src/sim_core` must be tightened to mirror OR natively when `physics_mode="openrocket"`.

### The Core Discrepancy Causes:
Our analysis shows that the Rust engine is currently under-calculating drag and ignoring structural mass. To fix this, we will port the following specific equations from OpenRocket's source code into the Rust engine:

### Implementation Steps:
1. **True Mass & CG Calculation (`mass_calculator.rs`)**:
   - Currently, `liftoff_mass` is hardcoded to a placeholder or loosely approximated. We must integrate the true volumetric mass calculations.
   - We will implement a recursive mass pass in `ast.rs`: `total_mass = sum(component.volume * material.density)`.
   - We will pull the exact propellant mass decay curves from the `.eng` motor files rather than assuming a static mass fraction.

2. **Base Drag Formulation (`aerodynamics.rs`)**:
   - OpenRocket applies a significant penalty for "Base Drag" (the low-pressure wake behind the rocket). The Rust engine currently undervalues this.
   - We will port OR's base drag equation: $C_{D,base} = \frac{0.029}{\sqrt{C_{D,fb}}} (M < 1)$, scaled for the Mach number and the ratio of the motor mount diameter to the body tube diameter.

3. **Fin Interference Drag**:
   - OpenRocket adds interference drag where the fins meet the body tube.
   - We will add the OR formula: $C_{D,int} = C_{D,fins} \times (1 + \frac{R_T}{R_T + C_R})$ where $R_T$ is tube radius and $C_R$ is fin root chord.

4. **Transonic Wave Drag Spike**:
   - The Rust engine currently estimates the transonic drag spike. We will strictly map the `calc_ogive` and `interpolate_linear` methods in `openrocket_nose.rs` to output the exact arrays generated by OR's `AeroCalculator`.

### Execution Timeline:
By feeding the true mass to the Rust trajectory solver and adding Base + Interference drag, the baseline Rust prediction will get within ~5% of OpenRocket. The CKG Delta Feedback (Option 2) will then automatically crush that remaining 5% error margin to near 0%, yielding a perfectly accurate, hyper-fast genetic design loop for OSIFOG missions.
